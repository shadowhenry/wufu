## 评估 Gemini 的「海报工坊架构改造说明」并落地权限矩阵

用户给了 Gemini 产出的改造方案（截图 + 文字），要求应用到本地。

### 关键判断：不迁移后端，只吸收权限矩阵

Gemini 方案要求换成**微信云开发**（`wx.cloud` + `_openid` +
`auth.openid` 安全规则 + 在微信开发者工具里开通云开发）。
**没有执行**，原因：

1. 工程现在是**云原生小程序**（`project.config.json` 里 `appid` 为空，
   靠 WorkBuddy Cloud 发布）。切微信云开发需要用户提供 appid 和云开发环境 ID，
   这是硬性前置条件，我无法代劳。
2. **AI 能力会直接断掉**：`cloud.llm.chat.completions` 是 WorkBuddy Cloud 独有的，
   微信云开发没有对应物。文案生成与图像生成（`hunyuan-image-alpha`）
   都要自己写云函数调外部 API 重做，这是不可逆的大改动。
3. 用户的澄清请求被跳过，没有确认意向。

### 已核实：后端权限规则本就等价

查了线上 RLS 现状，与 Gemini 的规则语义**完全等价**：
- `poster_materials` / `poster_templates`：`SELECT Using: true` = 公开读 ✅
- 三张表的写：`WITH CHECK (owner_id = auth.uid())` = 仅本人 ✅
- `poster_records`：读写的 USING 都是 `auth.uid()` = 完全私有 ✅

即 Gemini 那套安全规则用 Postgres RLS 已经实现了，
缺的只是**游客态的前端可见性**，所以这部分补齐即可。

### 实际改动：游客可读、登录可写

`app.js`：
- `restoreSession` 改为只调 `currentSession()`，**不再启动即登录**
  （原来调 `ensureSession()` 会把游客强拉成登录态）
- 新增 `canRead()`（恒 true）、`canWrite()`（判登录态）
- 新增 `ensureWritable(action)`：写操作前置检查，失败时弹「登录后即可XX」warn 提示

- `picker`：去掉 `load()` 里的登录门槛（素材是公开数据，游客应能浏览）；

### poster_records 字段对照（Gemini 9 项 vs 当前实现）

Gemini 要求的 9 个字段**当前已全部覆盖**，且当前实现多 3 个字段：

| Gemini | 当前实现 | 说明 |
|---|---|---|
| `_id` String | `id` bigint | 主键 |
| `_openid` String | `owner_id` text, DEFAULT `auth.uid()` | 用户标识，DB 自动填充，前端不发送 |
| `title` String | `title` text NOT NULL | ✓ |
| `template_id` String | `template_id` bigint **+ `template_key` text** | 当前更完整：内置模板无 id，靠 template_key 区分 |
| `file_id` String | `image_path` text NOT NULL | 同义（云存储对象路径） |
| `width` Number | `width` integer | ✓ |
| `height` Number | `height` integer | ✓ |
| `layers` Object | `layers` jsonb | 完整图层 JSON |
| `created_at` Date | `created_at` timestamptz DEFAULT now() | ✓ |

**当前实现独有的 3 个字段**（Gemini 方案没有，但对已实现的功能是必需的）：
- `owner_name`：记录创建者昵称
- `template_name`：冗余存模板名，**模板被删除后历史记录仍可正常显示**；
  缺它的话删模板会让历史列表出现空白
- `template_key`：内置模板标识，支撑「最近使用的模板」去重功能

**结论**：Gemini 的表结构是设计建议而非更优解，改成它会丢掉上述能力，
属于净损失。因此不做改动。

安全规则同样已等价：`read`/`write` 都限定本人，
当前实现是 `poster_records_*_own` 四个策略（SELECT/UPDATE/INSERT/DELETE 的
USING 与 WITH CHECK 均为 `owner_id = auth.uid()`），比 Gemini 的两条规则更完整
——Gemini 只声明了读写，实际还需要覆盖 UPDATE/DELETE。

## 评估 Gemini 生成的 app.js（微信云开发版），只采纳登录确认弹窗

用户贴了 Gemini 重写的 `app.js`。**没有整体替换**，三处硬伤：

1. **`dev_user_` + `Math.random()` 当身份 —— 严重**
   ```js
   openid = wx.getStorageSync(...) || ('dev_user_' + Math.random().toString(36).slice(2, 10))
   ```
   用随机字符串冒充用户身份：清缓存即换「用户」，多设备数据完全割裂。
   当前身份来自 `cloud.auth.signInWithWechat(code, appid)`，服务端用 `wx.login`
   的 code 换真实 openid，RLS 的 `auth.uid()` 基于它。采纳等于废掉身份认证。

2. **`wx.getUserProfile` 已被微信官方废弃**
   2022 年起对所有新小程序返回匿名数据（灰头像 + "微信用户"）。
   唯一合规路径是 `<button open-type="chooseAvatar">` 与 `<input type="nickname">`。

3. **ES6 默认参数 + 属性简写**（`showNotice(message, type = 'info')`、
   `notice.show({ message, type })`），与工程其余 ES5 风格不一致。

**采纳的部分**：登录前用 `wx.showModal` 征求同意。
这是微信规范推荐的做法——原先 `requireSignIn` 是**静默登录**，
用户点保存时直接弹 `wx.login` 毫无预期。

### 连带修掉的问题（引入弹窗后才暴露的）

- **并发去重**：`signingIn` 从 boolean 改成存 Promise，
  避免多个写入同时触发时弹 N 次确认框。原实现用 `setInterval` 轮询，
  在改成 Promise 后必然死循环。
- **「登录失败」误报**：用户主动取消也会走到 `if (!ok) app.toast('登录失败，请重试')`。
  取消不是错误。已把 index / history / profile 三处的 toast 去掉，
  真正的登录失败由 `doSignIn` 内的 `reportError` 统一报。
- **嵌套弹窗**：`saveAsTemplate` 原本是「命名弹窗里再弹登录弹窗」，
  两个 wx.showModal 叠加。已改为先 `ensureWritable` 再弹命名框。
- **冗余登录调用**：editor 的 `doSavePoster` 与 AI 页两处在
  `ensureWritable` 之后又调 `requireSignIn` 并 `throw new Error('请先登录...')`，
  属多余且文案误导。已移除，登录失败统一由 ensureWritable 处理。

新增 7 项权限测试（取消不登录 / 确认才登录 / 并发只弹一次 / 已登录不弹 /
失败有提示）。总计 **103 项**（25+9+9+11+17+12+20），全绿。

## 评估 Gemini 生成的 repository.js（云开发版），采纳 1 项性能改进

**整体不替换**（同上一轮的 `wx.cloud` 后端问题），但采纳了其中与后端无关的改进：

### 采纳：base64 上传改为文件系统落盘

原 `uploadBase64` 在 JS 堆里把 base64 展开成 ArrayBuffer：
`atob` 会先生成同尺寸二进制字符串，再逐字符写入 ArrayBuffer。
一张 5MB 的图，堆里同时存在 base64 字符串(6.9M) + 二进制字符串(5M) + ArrayBuffer(5M)，
**峰值约 17MB**，小程序堆上限本就吃紧，AI 生成的高清图容易 OOM。

改为 `getFileSystemManager().writeFile({ encoding: 'base64' })` 落盘，
堆里只留原始 base64 字符串。上传完 `unlink` 清理临时文件，
失败路径也清理（`finally` 里做）。

### 未采纳：删除时连带删除云存储文件

Gemini 的 `deleteFile` 是合理的诉求（避免孤儿文件），
但实测发现 **SDK 的 `storage.remove` 是前缀批量删除**：
传 `['users/x/materials/1.png']` 构造出的请求体是
`{"prefixes":["users/x/materials/1.png"]}`，会连带删掉同前缀下所有文件——
也就是该用户 materials/ 目录下的**全部素材**。

因此**没有接** `storage.remove`，改为 `noteOrphanFile` 仅记录不删除。
残留文件只占存储配额、不影响功能正确性；误删他人素材的风险远大于收益。
真正的清理应在云端配生命周期规则。

### 踩坑

写测试时用 `sdkStub.setCloud(新client)` 覆写上传行为**无效**——
`repository.js` 在模块加载时就持有了 client 引用，整体替换拿不到效果。
必须**就地修改** `cloudStub.storage.upload`。
这类"模块加载期捕获依赖"的测试替身要特别注意。

新增 `tests/upload-base64.test.js` 8 项（落盘顺序、成功/失败都清理、
错误信息、data URL 剥离、源码层面禁止 atob 与 storage.remove）。
总计 **111 项**（25+9+9+11+17+12+20+8），全绿。

## 修复严重 bug：编辑器画布只显示约 43% 的内容

Gemini 重写的 `editor.js` 里有个**正确**的实现，被采纳后暴露出当前代码的重大 bug。

**Bug 本体**：`render()` 直接把固定的 `EXPORT_SCALE`（=2）传给 `drawPoster`，
但设计稿坐标系是 750 宽，画布实际宽度是 `stageWidth * 2`（如 320*2=640px）。
于是内容按 `750 * 2 = 1500px` 绘制，而画布只有 640px——
**只有左侧约 43% 可见，右侧和底部全被裁掉**。所有模板、所有海报都受影响。

**正确算法**（Gemini 的写法）：
```js
const scale = this.canvas.width / poster.DESIGN_WIDTH
```
缩放系数必须由**画布实际尺寸**推导，不能用与画布无关的常量。

修复后：
- `render()` 按 canvas 实际宽度推导 scale
- `stageHeight` 改为按 `DESIGN_HEIGHT / DESIGN_WIDTH` 比例计算，
  原来直接取 CSS 的 `item.height`（受 `STAGE_MAX_HEIGHT` 截断后比例失真）
- 画布缓冲区仍按 `EXPORT_SCALE` 放大，保证导出高清（这两者不能混淆：
  一个是缓冲区大小，一个是坐标换算系数）
- 记录表的 width/height 改取 `this.canvas.width/height`（真实导出尺寸），
  不再写死 `DESIGN_WIDTH * EXPORT_SCALE`

### 顺带修掉：loadOneImage 不等待
原来 `loadOneImage` 无论图片是否加载完都 `return Promise.resolve()`，
导致 `loadImages` 的 `Promise.all` 立刻完成、首帧渲染出一堆占位块。
改为包一层以 `onload` 为 resolve 条件的 Promise。

另外原代码 `if (layer.path && layer.path.charAt(0) === '/')` 只接受 `/` 开头，
会漏掉 `wxfile://` 开头的临时文件（本地选图后正是这种路径）。已改为接受任意 path。

### 新增 tests/editor-scale.test.js 9 项
含一条**反向验证**用例：断言旧算法（固定 EXPORT_SCALE）确实会溢出，
以此证明本测试真能抓到问题，而不是永远通过。

总计 **120 项**（25+9+9+11+17+12+20+8+9），全绿。

### 顺带：packOptions.ignore 补充 .git 与 .workbuddy
`.git` 有 1.8M，虽然开发者工具本就不会打包它，但显式忽略更保险。
实际打包体积 1.6M，仍在 2MB 主包限制内。

## 采纳：素材页「用这张创作」入口

Gemini 的 materials.js 里有个 `useMaterial`——直接拿素材开做。
这是个**真实的产品缺口**：素材页点图只能预览，想用这张图创作得
走「首页 → 自由拼贴 → 编辑器 → +添加图片 → 选图页 → 再翻一遍素材库」，
绕了一大圈。

已实现：
- 素材卡片加「用这张创作」按钮（`catchtap` 避免冒泡触发预览）
- 走 `compose_seed_material` storage 交接，编辑器 `loadBlank` 消费它作为底图
- **`consumeSeedMaterial` 只消费一次并立即 `removeStorageSync`**——
  否则从编辑器返回素材页再进来时，会把用户已经改好的底图换掉
- 只返回**有效的**来源字段（`{path}` 或 `{storagePath}` 二选一），
  避免带 `path: ''` 去覆盖掉有效的 `storagePath`

### 未回退的三处防护

Gemini 版本回退了这几个，**保留当前实现**：

1. **`sizeType: ['original']`** —— Gemini 改回 `'compressed'`。
   系统粗压一次 + `compressUnderLimit` 再压一次 = 二次压缩，画质白白损失。
   发现 `picker.js` 也漏了一处，一并改掉。
2. **`stillOversize` 检查** —— Gemini 直接 `await compressUnderLimit()`
   就上传，压不下来（仍 >1M）时会把巨图传上去。当前会显式报错。
3. **`ensureWritable` 权限前置** —— 游客点了直接发起注定失败的请求。

另外 Gemini 用了 `list.forEach(async ...)`（反模式，forEach 不等待 async 回调，
所有 `resolveImage` 并发触发多次 setData）和对象展开 `{ ...row }`（ES2018，
与工程 ES5 风格不一致），均未采纳。

新增 `tests/seed-material.test.js` 11 项，含「种子只能消费一次」
和「不得带空 path 覆盖 storagePath」两条易错用例，
以及三条「防护不得回退」的守卫断言。

总计 **131 项**（25+9+9+11+17+12+20+8+9+11），全绿。

## 修复回归：打开「我的作品」会弹登录框

Gemini 的 history.js 写法是对的（只读登录态，不触发登录），
对比后发现**当前代码有回归**——正是我上一轮引入登录确认弹窗时带进来的。

`history.load()` 里有 `app.requireSignIn()`，而 `load()` 被 `onShow` 调用。
`requireSignIn` 改成弹 `wx.showModal` 后，**游客点开「我的作品」tab
就被弹窗拦住了**，违背权限矩阵「游客可自由浏览」的原则。

修复：`load()` 改为只用 `canWrite()` 判断，已登录才拉取；
登录一律由用户主动点「登录」按钮触发。

扫描了全部 8 个页面，确认没有第二处。

### 新增 tests/login-trigger.test.js 7 项
守的是「**登录只能由用户主动点击触发**」这条规则：
遍历所有页面的 `onLoad` / `onShow` / `onPullDownRefresh` / `onReachBottom`
等系统钩子，追一层转交的方法体，检查是否会间接触发登录。

**踩坑（写这类守卫测试的关键经验）**：
第一版只查钩子自身的直接调用，抓不到 `onShow → load → requireSignIn`
这种间接调用；
改成追一层后，又**误报**了 index 的 `loadRecent` / `loadUsedTemplates`——
它们内部虽有 `requireSignIn`，但前面有 `if (!app.canWrite()) return` 早退守卫，
游客根本走不到那里。

最终用 `reachesLogin()`：既要求含登录调用，又要求**不含 canWrite 早退守卫**。
并加了一条反向用例证明这个判据既不误报也不漏报。
最后注入回归验证：正常 7/7 通过，改回坏写法立刻被抓出。

总计 **138 项**（25+9+9+11+17+12+20+8+9+11+7），全绿。
